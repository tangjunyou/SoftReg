# Phase 0 · 项目工厂（没有项目时，先造一个可申请软著的真实软件）

适用判断：用户说"我没有项目 / 帮我做一个能申请软著的软件"时进入本阶段。用户已有真实项目则直接进 Phase 1。

## 合规前提（先向用户说明，不可跳过）

- 登记的软件必须是**真实存在、真实可运行**的软件。AI 辅助编程（Copilot / agent 编码）是行业常态，允许；但软件本身要能跑、能演示、代码是其最终形态——这是"开发完成"的法定含义（全部固定在有形载体上）。
- 不做：批量套改模板生成多个"皮 software"、伪造开发过程。官方 AI 审查重点打击的就是批量雷同与纯 AI 文档。
- 本阶段产出的是真实软件 + 其源代码，不是"软著材料生成器"。

## 1. 选题引导（和用户聊清楚，给出 3 个候选方向）

选题四条思路（按用户背景推荐）：

1. **自身痛点**：用户工作/学习/生活中真实存在的重复劳动或信息管理需求（最佳——业务真实，写手册有话说）。
2. **行业移植**：把某个熟悉行业的线下流程做成小系统（报名、台账、巡检、排班、点餐、库存）。
3. **课程/作业放大**：把某个课程设计扩展成完整系统。
4. **开源思路再实现**：借鉴某类工具的设计思路，**独立实现**界面与代码（界面和代码相似度不能高，否则原创性存疑）。

选题确认门禁：用户从候选中选定方向，并确认软件定位一句话（"给谁用什么解决什么问题"）。

## 2. 命名与版本（全局唯一口径，写进项目 README）

- 软件全称：`某某某 + 行业/领域词 + 系统/软件/平台/工具`，简短明确、针对性强，不得违反公序良俗。
- 版本号：**V1.0**（首次申请固定建议值）。项目内所有出现版本号的地方（package.json、页面 footer、关于对话框、README）统一为 V1.0，避免出现 v0.x 冲突。
- 最好不用简称；若用，全局唯一。
- 命名确认门禁：用户确认全称后，此名称将成为后续所有材料、页眉、手册的唯一口径。

## 3. 开发要求（决定材料质量，开工前定死）

| 项 | 要求 | 原因 |
|---|---|---|
| 代码量 | 非空源码行 ≥ 3200（建议 8000~15000） | 前 30 + 后 30 页共需 3120 行材料（52 行 × 60 页）；余量防不足 |
| 可运行 demo | 必须能启动、有测试数据、界面有内容 | 操作手册每个功能模块要真实截图 |
| 技术栈 | Web 前端（React/Vue/原生）优先 | 截图方便；代码审核员可读性高 |
| 长行控制 | 避免内联超长 className/SVG path（>200 字符的行尽量少） | 超长行会迫使 PDF 排版降字号（见 build_code_pdf 布局报告） |
| 代码卫生 | 无第三方版权声明头、无 license 正文混入业务代码、无 node_modules/构建产物 | 鉴别材料不能含他人版权内容 |
| 业务逻辑 | 有真实业务规则（校验、状态流转、数据加工），不是纯脚手架 | 防"通用框架程序"补正意见 |

开发方式：agent 主导编码（正常 vibe coding 流程），**用户必须实际参与**：跑起来、点一遍、提修改意见——这些真实交互是后续手册截图和功能描述的素材来源。

## 4. 完成验收（进 Phase 1 前的门禁）

1. `demo` 启动成功，核心流程可走通，界面有测试数据。
2. 非空源码行数达标（用 `analyze_project.py` 统计）。
3. 项目内版本号全局统一为 V1.0，无残留旧名/旧版本。
4. 用户确认："这个软件就是我要登记的软件，功能就是这些。"

验收通过后进入 Phase 1 生成材料。
